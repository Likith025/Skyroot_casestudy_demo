
# Flight Sequencer Simulation (Single-Core FreeRTOS)

## Overview

This project is a **single-core simulation** of the Flight Sequencer case study. It uses CMSIS-RTOS v2 APIs with FreeRTOS underneath to model periodic tasks, data flow, feedback and basic health monitoring.

The purpose is to test the task flow and scheduling before integrating real sensors and communication hardware. This is **not a complete implementation of the original dual-core architecture**.

## Features

- Periodic sensor tasks that generate simulated data.
- A Flight Sequencer task that runs every 10 ms.
- A Slow Computation task that runs every 200 ms.
- A Supervisory task that checks task health using heartbeat counters.
- A Logger task that sends debug messages through USART3.
- Basic execution-time measurement using the Cortex-M DWT cycle counter.
- Two-slot mailboxes for sharing the latest available data.
- Simulated execution times based on the case study assumptions.

## Task Structure

| Task | Period | Purpose |
|---|---|---|
| `Sensor1Task` | 5 ms | Generates simulated Sensor 1 data and publishes it to a mailbox. |
| `Sensor2Task` | 10 ms | Generates simulated Sensor 2 data and publishes it to a mailbox. |
| `SequencerTask` | 10 ms | Reads sensor data and feedback, performs placeholder calculations and publishes a snapshot. |
| `SupervisorTask` | 10 ms | Checks heartbeat counters, reports faults and simulates watchdog decisions. |
| `SlowTask` | 200 ms | Simulates a long-running calculation and publishes feedback. |
| `LoggerTask` | Event-driven | Reads queued messages and sends them through USART3. |

The tasks use CMSIS-RTOS v2 priority settings. Sensor tasks have the highest configured priority, followed by the Sequencer, Supervisor, Slow task and Logger.

## Data Flow

1. `Sensor1Task` and `Sensor2Task` generate sample values and publish them to `mb_s1` and `mb_s2`.
2. `SequencerTask` reads the latest sensor values and feedback from `mb_fb`.
3. The Sequencer performs placeholder calculations and publishes a snapshot to `mb_snap`.
4. `SlowTask` reads the snapshot, simulates its computation and publishes feedback to `mb_fb`.
5. `SupervisorTask` checks heartbeat counters and reports tasks that stop making progress.
6. `LoggerTask` sends queued diagnostic messages through USART3.

## Timing Configuration

The following execution times are simulated:

| Operation | Configured time |
|---|---:|
| Sequencer computation | 2 ms |
| Supervisor computation | 0.3 ms |
| Slow computation | 60 ms |
| Sequencer deadline | 10 ms |

The `busy_us()` function simulates CPU work using the DWT cycle counter. Periodic tasks use `osDelayUntil()` to maintain their execution intervals.

These values are placeholders based on the case study assumptions. They are not guaranteed execution times for a final application.

## Single-Core Architecture

This implementation runs entirely on **one CPU core**. All tasks share the same RTOS instance and compete for CPU time according to their priorities.

The original case study proposes a dual-core AMP architecture:

- **Core 0:** Handles sensor interrupts, the Flight Sequencer and the Supervisory task.
- **Core 1:** Runs the Slow Computation task separately.

The current simulation does not implement this separation or test cross-core communication. It is intended to demonstrate the basic software flow on a single core.

## Implementation Limitations

The current version simplifies several parts of the original design:

- Sensor data is generated by software. Actual UART reception, DMA and idle-line detection are not implemented.
- Frame parsing, CRC validation and sequence-number checks are not implemented.
- The actuator command is calculated as a placeholder; actual UART 3 DMA transmission is not implemented.
- Mailboxes carry four `int32_t` values instead of the complete sensor frames and snapshot structure.
- Mailbox reads do not verify that a slot remains unchanged during copying. The synchronization mechanism needs improvement before production use.
- Feedback does not include the source-cycle tag used in the full case-study design.
- Sensor-data age and stale-feedback checks are not implemented.
- The Supervisor does not monitor actuator transmission health.
- The watchdog action is represented by a software counter. A real hardware watchdog is not refreshed by this simulation.
- The Logger uses a message queue, but sends messages through a blocking HAL UART transmit call.

Therefore, successful execution demonstrates the basic task flow and periodic scheduling. It does not prove that the complete system meets the original timing, safety or concurrency requirements.

## Requirements

The project is intended for an STM32 environment with:

- STM32 HAL.
- CMSIS-RTOS v2.
- FreeRTOS as the underlying RTOS.
- USART3 for diagnostic output.
- A Cortex-M DWT cycle counter for timing measurement.

The project must provide the required declarations and configuration, including `flight_sequencer_app.h`, `main.h`, the UART handle `huart3` and the RTOS configuration.

## Integration Steps

1. Add the source file to the STM32 project.
2. Enable CMSIS-RTOS v2 and configure FreeRTOS.
3. Configure USART3 and make sure `huart3` is available.
4. Confirm that the target supports the DWT cycle counter.
5. Call `FlightSequencer_Start()` after hardware initialization and before `osKernelStart()`.
6. Confirm that the RTOS tick rate supports the 5 ms, 10 ms and 200 ms task periods. The example assumes a 1 ms tick.
7. Verify stack sizes, priorities and runtime behaviour on the target hardware.

## Expected Output

The Logger task prints periodic status messages, including:

- Sensor frame counts.
- Sequencer execution time and deadline status.
- Supervisor health status and fault reports.
- Slow task execution time and feedback values.

The exact output depends on task scheduling, queue availability and target timing.
